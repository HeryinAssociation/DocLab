# DSH → Doclab → Zotero 打通方案

日期：2026-10-17。本文是实施方案，新增接口、工作区和插件均尚未实施，不代表已经可以调用。

## 1. 目标与总体决定

直接复用现有 Doclab。用户在 DSH 的专用工作区发送一本新书 PDF，附一句“处理并归入某分类”；DSH 调用 Doclab 完成 OCR、索引、AI 核校、分章导出、验证和 Zotero 附件归档，最后返回条目与处理摘要。

不再开发一套转换引擎。DSH 负责接收文件和 AI 核校决策；Doclab 负责所有处理、状态、验证与归档编排；Zotero 插件只负责应用内文件／条目操作。日常操作统一走 Doclab MCP，内部可以调用 MinerU、Doclab Python 内核和 Zotero 插件。

目标使用约定：一次性指定默认 Zotero 库、分类、核对深度、导出深度和允许的新建／追加范围；之后每本书在此范围内自动执行，只有证据冲突、条目身份不明或验证失败时才要求补充信息。方案阶段不改变现有 Lab 只读配置。

## 2. 已核实的基础

| 部分 | 本机证据与判断 |
| --- | --- |
| Doclab | 已有 CLI、stdio MCP 及 16 个工具；有 PDF 分片 OCR、EPUB 解析与装订、目录 JSON 往返、人工层、页码修订单、导出与四道校验 |
| DSH | 本机 CLI 包版本 0.1.7-rc.2；安装包说明支持普通文件持久存储、附件句柄／映射路径、stdio MCP 和工作区 skill；尚未实测 PDF 上传全流程 |
| DSH skill 发现 | 支持 `<projectRoot>/.dsh/skills/<name>/SKILL.md`；现有 Doclab `skills/` 目录不等于已经被 DSH 自动加载 |
| Zotero | 本机安装版本 10.0.5；已读取本机应用包中 Attachments.importFromFile 的 file、parentItemID、contentType 等参数 |
| 现有 Zotero MCP | JingyeLab 的实现硬编码 GET，只读；不能通过打开配置开关就获得写能力 |
| 旧 Connector | 当前本机源码仍要求 saveAttachment 使用存活 session 的 connector key 找父条目，不适合作为任意既有条目附件写入的主通路 |

现有 `doclab.py/core` 是唯一业务实现。新增 MCP 继续做薄封装；新增任务模块编排已有函数，不再实现一套目录推断、校准或渲染算法。

## 3. 用户端工作区

建议工作区根目录为 `C:\Users\jingye\Documents\Codex\Doclab-Inbox`，与 Doclab 程序目录、JingyeLab 研究项目分开。目录目前尚未创建。

```text
Doclab-Inbox/
├─ AGENTS.md                     自动入库范围、异常规则与入口约定
├─ .dsh/skills/doclab-proofread/  已有核校 skill 的部署副本
├─ config/intake.local.json      库／分类／深度／权限及服务连接设置
├─ inbox/                        已接收的 PDF 副本与接收记录
└─ receipts/                     任务结果、Zotero keys、核验摘要
```

Doclab 本身继续使用其 `_work/<source_id>` 与 `out/<source_id>/L<N>`。专用工作区不保存第二套可编辑索引；接收记录指向 Doclab 的 source_id 和 job_id。

DSH 使用专用 agent preset；如当前 profile 无法可靠限制工具与指令作用域，使用从 web 模板派生的独立 profile。必须检查实际配置树，保证新书归档工具不会无意开放给现有只读研究会话。profile 与工作区不是同一概念，不能仅换目录就假设权限已隔离。

文件接收优先使用 DSH 解析后的附件标识与映射路径，不让模型猜测 `~/.dsh/attachments` 目录。适配器验证类型、字节数和 SHA-256，复制到 inbox 后交给 Doclab。PDF 文件字节由工具读取／上传 MinerU，不经过模型上下文。需要实测浏览器上传、大 PDF、Unicode 文件名和重启后路径可用性。

## 4. 完整流程与阶段闸门

```text
DSH 收到 PDF
  → 解析附件路径、哈希去重、创建／恢复任务
  → Doclab ingest（复用已完成 OCR，缺片续跑）
  → pagecal → outline → 机械检查
  → 请求 AI 核校：目录结构 + 必要正文／原页证据
  → 演练并写入人工层，重算；有改动再核查受影响部分
  → export → verify + 全书内容覆盖检查
  → 核对题录、查重、形成 Zotero 归档计划
  → Zotero 插件执行计划 → 逐附件回读核验
  → DSH 返回条目与处理摘要
```

正常书自动完成。信息缺失或异常进入 `needs_input`／`needs_review`，状态与证据落盘；不要声称所有书都能无人工干预完成。

### AI 核校规则

- 全部目标深度目录节点按父章分批检查，不能只看机械 findings，避免漏掉语义层级错误。
- 正文按需读取，页码看观测冲突、原页及受影响区间；模型必须具备看图能力或有另外经过验证的视觉核校路径，纯文本模型不得声称已视觉核实。
- 目录编辑继续生成完整 JSON 副本并走 tocio；对模型提供增量操作，服务端负责与完整基线合并，不能把分页节点列表作为整书替换。
- 页码走 fixplan anchor，确认分片内 0 基索引及向后覆盖范围。改页码后重取目录基线。
- 具体理由与原书位置随改动保存；不是根据“置信度高”就写回。正文不可确认的合成节点保留其证据级别。
- 默认最多两轮自动修正复查；仍冲突则保留报告，避免无限反复调用模型。

### 导出闸门

保留原有 G1–G4，同时补齐“全部应保留源块 → 导出区间”的覆盖检查。现有 G2 仅检查已进入 export_index 的块，不能独立证明全书无遗漏；深层切分的父级直属正文需重点处理。

content missing、未解决的错层／错定位、错误书籍身份禁止进入自动归档成功态。无可靠印刷页码可以明确采用 section_only；这种可解释 warn 不应为了消除警告而伪造页码。默认自动归档只接收通过既定内容／结构闸门的版本；疑难书保留本地产物等待补充。

## 5. Doclab MCP 扩展：对模型只暴露少量日常工具

原 15 工具保留供调试。专用 DSH preset 日常建议只暴露下列 6 个高层工具；名称均为拟新增。

| 拟新增工具 | 输入与职责 | 默认返回 |
| --- | --- | --- |
| `doclab_book_start` | 已解析 PDF 路径、任务配置；启动或恢复已识别任务 | job_id、source_id、stage、next_action |
| `doclab_job_status` | job_id、已见状态版本，可选有界等待 | 变化后的阶段、计数、错误与下一步；无长日志 |
| `doclab_review_read` | job_id、类型、父章／块范围／游标 | 紧凑目录、问题证据、完整指定原块或指定页图；带覆盖与截断标记 |
| `doclab_review_apply` | job_id、base_revision、操作列表、evidence；支持 dry_run | 差异摘要、实际成功／失败项、新 revision |
| `doclab_book_finalize` | job_id、已核校 revision、导出配置 | 导出清单路径、四闸门与覆盖检查摘要、待解决项 |
| `doclab_archive_book` | job_id；先 prepare 生成持久 plan_id，再按计划提交／恢复 | 条目 key、附件计数、逐文件状态、核验结论 |

archive 的 prepare/commit 分离是防止计划与实际写入不一致；在用户已设定的自动归档授权范围内由流程自行提交，不要求每本书再手点确认。commit 必须绑定 plan_id、源内容哈希与导出 revision；模型不能提交任意文件路径来替换附件。

基础层需补 `audit`、`fix` 和完整原块／原页读取能力，供以上工具调用；不必全部追加到模型工具目录。review_apply 内部继续使用 tocio/fixplan，增加源身份、全部操作预校验、快照与失败恢复，不宣称现有逐项 apply 已经原子化。

stdio MCP 启动、重连、tools/list 都不能自动开始 OCR 或写入 Zotero。耗时任务由独立 Doclab worker 执行，MCP 返回任务编号，不随客户端超时杀死 worker。

## 6. 异步任务如何持续运行

状态建议为 `received → ocr_running → indexed → needs_ai_review → reviewed → exporting → validated → archive_prepared → archiving → completed`，另有 needs_input、needs_review、failed。状态加单调递增 revision 和最近事件序号；阶段完成后才推进，重启按持久记录恢复。

OCR、导出、验证、文件上传在 worker 中执行，不消耗模型推理轮次。AI 只在 needs_ai_review 或确实需要决策时运行。

**“后台任务完成”不自动等于“DSH 会话会醒来”。** 需实现并验收 DSH 侧任务适配器，订阅 Doclab 阶段变化，按 job_id + event_seq 去重，将需要 AI 处理的事件交回指定会话；最终完成只发一次摘要。该适配器使用 DSH 实际会话／任务能力，接口须在实施中确认，不编造已存在的唤醒 API。

通知恢复前可以使用前台有界长轮询作为临时调试，但它不能通过“无人值守、关页面后继续”的最终验收。状态轮询尽量由程序承担，避免每隔几秒调用一次模型。DSH 与 Doclab 重启后恢复未完成任务，不能直接重新 ingest --force。

## 7. Zotero 写入：推荐本地小插件

推荐在 Zotero 10.0.5 内安装一个用途有限的 Doclab 归档插件，由 Doclab MCP 经本机接口调用。插件利用 Zotero 对象与附件 API 操作数据；不从外部程序直接改 Zotero SQLite。它不是另一个转换系统。

插件应支持：按库／分类 key 核实目标、查找指定父条目、创建最小专著条目、向既有或新条目导入受管理文件、枚举并回读附件、保存任务归档回执。现有只读 Zotero MCP 可以继续服务研究阅读。

不采用旧 Connector 会话方案作为主实现：它对父条目的定位依赖临时 session，难以可靠支持过一段时间给既有书籍追加章节。插件运行于 Zotero 本身，可以按真实父条目 key 操作。该设计依据已读取的本机应用接口，插件兼容、资源同步与批量回读仍需实际验收。

接口只监听本机、使用独立密钥、限定可写库／分类及已准备的输出目录，只提供归档动作，不开放任意 JS 执行。密钥不进入模型返回。默认只允许新建和添加当前任务的附件，不更改既有题录、不删除旧附件；版本更新另存新转换版本，清理旧版本须另有要求。

### 条目与附件识别

1. PDF 哈希相同且已有完成记录，优先返回现有结果；OCR 配置或工具版本不同则明确区分任务版本。
2. 使用 ISBN（如有）、作者、译者、版次、出版社等查重，不只依靠文件名／书名。相似但不确定的候选要求选择。
3. 新条目的书目数据来自版权页／书名页，缺失项留空并说明；关键身份无法判断则先生成 MD，不自动挂错书。
4. 确认库 ID、父条目 key 和分类 key 后形成固定归档计划，不依赖 Zotero 界面当前选中分类。
5. 每份附件保存角色、相对路径、SHA-256、转换版本及实际附件 key；超时先按回执与附件信息核查，再补剩余文件。

### 归档包

挂在同一个 book 上级条目下：原 PDF／EPUB、整书 EPUB、00-目录、各章节 MD、manifest、conversion_meta、校验报告与 coverage。2026-11-17 起不再生成完整 ZIP（按用户偏好排除），AI 核校报告只留本地；章节 MD 仍是研究 MCP 直接读取的入口，整书 EPUB 供阅读与交付。

独立附件进入不同 storage 目录后，不能继续假设原来的 `001_…md` 相对链接能跨附件打开。先导入章节、获取真实附件 key，再生成 Zotero 版目录链接；另保留 ZIP 内的原版目录。题录 key 与附件 key 分开记录。

章节中的图片需由插件在该章节受管理附件目录内保留其相对资源，使用 Zotero 文件接口及受控路径处理，并验证桌面读取与实际使用的同步方式；未验证前不宣称资源已经可迁移。完整 ZIP 是保真备份，不能用“ZIP 里有图”掩盖章节附件图片链接失效。

后续研究 MCP 如需读取图片，返回附件身份、图片路径／图像内容的专门结果，不把图片 base64 当正文文本返回。跨附件目录链接应以 Zotero 可用的条目链接形式生成，并实测选择／打开行为，不能仅做字符串替换就算通过。

### 提交与回读

归档不是跨全部附件的一次事务，按文件持久记录进度。失败则标为 partial，原书与已成功附件保留；续跑先核实父条目、版本、文件角色及哈希，只补未成功部分，不自动删除以模拟回滚。

完成要求逐文件读取回实际路径与哈希、确认父子关系和分类、验证目录定位及资源。Zotero 未运行时保留 validated 状态和准备计划，等待恢复后继续，不重跑 OCR。

## 8. Token 控制

| 机制 | 做法 |
| --- | --- |
| 文件不进上下文 | PDF、ZIP、MD 全量文件由工具传输；只让模型读必要片段 |
| 紧凑工具目录 | 日常挂载 6 个高层工具；研究／调试能力按实际 preset 隔离 |
| 简洁返回 | 默认结构化短摘要；详细日志和整书状态保存在 Doclab，显式请求才读取 |
| 目录分批 | 节点返回 key、level、title、位置及必要标记；父章上下文与游标完整，不遗漏节点 |
| 只复查变化 | 用 revision／证据哈希缓存未改变部分，修改后只重看受影响范围 |
| 无模型轮询 | 后台等待 OCR／Zotero，只在需要判断或最终结果时激活会话 |
| 无机械模型工作 | 哈希、复制、编号检测、覆盖检查、附件清点、失败续跑都交程序 |
| 有限修复轮次 | 两轮仍无法解决时输出具体疑问，不重复猜测 |

短返回设计目标：普通状态结果约数百 token 内，目录每次按章／约几十个节点返回，正文按需要限制块数；这是待实测预算，不承诺固定总 token 或节省百分比。图片按模型实际图像计费另计。MCP 只是调用协议，若返回整书正文仍会消耗大量 token。

## 9. 实施文件范围与顺序

| 步骤 | 修改范围 | 交付／通过条件 |
| --- | --- | --- |
| 1. 接通现有链路 | DSH 工作区、preset／必要 profile、技能发现、DOCLAB_PYTHON 路径 | 上传 PDF 能交给现有 Doclab，完成本地 MD；尚不自动写 Zotero |
| 2. Doclab 编排与核校 | mcp_server.cjs、doclab.py、拟新增 core/jobs.py 和 review 服务；复用现有模块 | 异步 OCR、结构化错误、增量核校、页码修正、全书覆盖校验与恢复通过 |
| 3. Zotero 插件与归档 | 拟新增 zotero-plugin/ 与 core/zotero_archive.py | 指定新／既有父条目导入附件、目录和图片可用、重试不重复 |
| 4. DSH 阶段通知 | 附件／任务适配器、同会话事件交回、回执展示 | 关页面／会话恢复后能继续，完成与异常准确通知 |
| 5. 样书验收 | 真实 PDF 与隔离测试条目，记录 token、耗时、问题清单 | 完整闭环、失败恢复和归档回读均通过，才启用日常自动流程 |

不要为入库去修改所有 JingyeLab 研究角色的只读约定。具体落地先检查 profile 的作用域隔离；用户确认本方案并要求实施时，将书籍入库的授权范围写入新工作区配置，不反复要求其批准每个确定性步骤。

## 10. 必过验收用例

- 一本清晰 PDF：上传后自动处理、核校、导出、挂到新 book 条目并能从 Zotero 分章读取。
- 一本跨片／页码异常 PDF：锚点作用区间正确，缺页不编造；无法解决时不会自动标记完成。
- 已有专著：准确追加到指定 key，不新增重复上级条目，不覆盖原有附件。
- 同 PDF 重发：复用任务与完成回执；不重复 OCR、不重复挂附件。
- 修改导出深度：形成新转换版本，旧版本可追溯，校验不混用 export_index。
- OCR／MCP／DSH 中断：从持久阶段恢复，重连不触发重复副作用。
- Zotero 在第 N 个附件时断开：回读已成功项，只补剩余文件。
- 目录链接和图片：在 Zotero 真实附件位置可用；需要跨设备使用时再验证同步后的路径。
- 省 token：记录真实模型输入／输出用量，确认没有整书正文、完整日志或无意义轮询进入模型。

验收通过后，日常回复可以只包含“已归入哪本书／哪个分类、章节数、目录链接、核校结论及未决项”。任务完成状态必须同时意味着本地处理通过和 Zotero 回读通过。
